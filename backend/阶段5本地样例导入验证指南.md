# 阶段 5 本地样例导入验证指南

本文用于验证 `backend/开发顺序.md` 的阶段 5。所有命令均以项目根目录
`~/桌面/design/DataBase` 为基准，数据库使用已经完成迁移的
`transit_system_migration_test`。

## 1. 样例基准

本次验证使用：

- `bus_line_raw_gaode.json`：高德线路样例，2 个方向，每个方向 29 条站序；
- `bus_stop_by_name.json`：高德站点样例，2 个站点；
- `raw_result.json`：上海接口样例，共 50 条附近线路站点记录。

解析和去重后的确定数量如下：

| 项目 | 数量 | 说明 |
|---|---:|---|
| 高德线路方向 | 2 | `310100015144`、`310100015143` |
| 每个高德方向的站序 | 29 | 序号均为 1 至 29 |
| 高德唯一物理站 | 36 | 两个方向之间有重复站点 ID |
| 上海原始记录 | 50 | `nearByTrafficLineStop` 数组长度 |
| 上海唯一线路方向 | 37 | 按 `(lineId, upDown)` 去重 |
| 包含 `sai` 的记录 | 43 | 其余记录不创建空到站快照 |
| 去重后的到站快照 | 42 | 一组线路/物理站在样例中重复，跳过 1 条 |
| 去重后的调度快照 | 37 | 每个线路方向只保存一条 |
| 调度车辆明细 | 95 | 取每个线路方向首次出现的调度数组 |

在业务表原本为空的数据库中，完整导入后应得到：

| 表 | 预期数量 |
|---|---:|
| `lines` | 39 |
| `stops` | 39 |
| `line_routes` | 58 |
| `arrival_infos` | 42 |
| `dispatch_schedules` | 37 |
| `dispatch_cars` | 95 |

`lines = 2 + 37`。`stops = 36 个高德站 + 3 个仅由上海样例发现的站`。

如果测试库在本次验证前已有其他业务数据，不能直接比较表总数，应比较导入前后的数量差值。

## 2. 前置检查

进入后端目录并启用虚拟环境：

```bash
cd ~/桌面/design/DataBase/backend
source ../.database/bin/activate
```

确认 `.env` 指向测试库：

```bash
grep '^DATABASE_URL=' .env
```

数据库名必须是 `transit_system_migration_test`，不能是开发库或生产库。

连接 MySQL：

```bash
mysql -h 127.0.0.1 -P 3306 -u transit_app -p transit_system_migration_test
```

在 MySQL 中确认迁移版本和十张业务表：

```sql
SELECT version_num FROM alembic_version;

SELECT COUNT(*) AS business_tables
FROM information_schema.tables
WHERE table_schema = DATABASE()
  AND table_type = 'BASE TABLE'
  AND table_name <> 'alembic_version';
```

预期结果：

```text
version_num: d7d568f105a9
business_tables: 10
```

## 3. 执行完整导入

退出 MySQL，或者另开终端，在 `backend` 目录执行：

```bash
python -m app.commands.import_samples \
  ../bus_stop_by_name.json \
  ../bus_line_raw_gaode.json \
  ../raw_result.json
```

预期输出结构：

```text
run=<ID> source=amap status=success received=2 inserted=<数量> updated=<数量> errors=-
run=<ID> source=amap status=success received=2 inserted=<数量> updated=<数量> errors=-
run=<ID> source=shanghai status=<success或partial> received=50 inserted=<数量> updated=<数量> errors=<摘要或->
```

上海运行允许为 `partial`。计划发车只有 `HH:mm`，如果执行导入时部分时间已经过去且不能
可靠判断属于次日，解析器会把 `planned_departure_at` 留空并记录问题，但其他有效记录仍会提交。

如果此前已经用相同路径成功导入过高德样例，高德两行会复用原运行 ID。这是 request key
幂等保护，不是漏执行。

## 4. 检查运行记录

连接 MySQL 后执行：

```sql
SELECT
    id,
    source,
    task_type,
    request_key,
    status,
    received_count,
    inserted_count,
    updated_count,
    skipped_count,
    failed_count,
    error_message
FROM `ingestion_runs`
ORDER BY id;
```

预期：

- `line_import` 收到 2 个高德线路方向；
- `stop_import` 收到 2 个高德站点；
- 最新 `nearby_import` 收到 50 条上海记录；
- 最新上海运行的 `skipped_count` 至少为 1，因为重复到站快照被跳过；
- 最新运行状态为 `success` 或 `partial`，不能是 `running` 或 `failed`；
- 之前因唯一键错误产生的 `failed` 运行记录可以保留，它用于证明失败可追踪。

早期版本的失败处理可能留下 `running` 状态的历史记录。这不是有效的运行中任务，可以在确认
同一 request key 已有后续成功运行后，将旧记录修正为 `failed`：

```sql
UPDATE `ingestion_runs`
SET status = 'failed',
    finished_at = CURRENT_TIMESTAMP(3),
    error_message = '历史导入失败：重复到站快照触发唯一约束'
WHERE id = 3
  AND status = 'running';
```

不要删除后续的成功运行记录。

## 6. 验证高德双方向和站序

```sql
SELECT
    l.id,
    l.line_name,
    l.direction,
    l.amap_line_id,
    COUNT(r.id) AS route_count,
    MIN(r.sequence_no) AS first_sequence,
    MAX(r.sequence_no) AS last_sequence
FROM `lines` AS l
LEFT JOIN `line_routes` AS r ON r.line_id = l.id
WHERE l.amap_line_id IS NOT NULL
GROUP BY l.id, l.line_name, l.direction, l.amap_line_id
ORDER BY l.direction;
```

预期核心字段：

```text
+-----------+----------------+-------------+----------------+---------------+
| direction | amap_line_id   | route_count | first_sequence | last_sequence |
+-----------+----------------+-------------+----------------+---------------+
|         0 | 310100015144   |          29 |              1 |            29 |
|         1 | 310100015143   |          29 |              1 |            29 |
+-----------+----------------+-------------+----------------+---------------+
```

检查方向 0 的完整站序：

```sql
SELECT
    r.sequence_no,
    s.stop_name,
    s.amap_stop_id,
    r.shanghai_stop_id
FROM `line_routes` AS r
JOIN `lines` AS l ON l.id = r.line_id
JOIN `stops` AS s ON s.id = r.stop_id
WHERE l.amap_line_id = '310100015144'
ORDER BY r.sequence_no;
```

预期 29 行，`sequence_no` 从 1 连续到 29。第一站高德 ID 为 `BV10030918`，末站高德
ID 为 `BV10029143`。

检查是否存在不连续或重复站序：

```sql
SELECT
    line_id,
    COUNT(*) AS route_count,
    COUNT(DISTINCT sequence_no) AS distinct_sequences,
    MIN(sequence_no) AS min_sequence,
    MAX(sequence_no) AS max_sequence
FROM `line_routes`
GROUP BY line_id
HAVING route_count <> distinct_sequences
    OR min_sequence <> 1
    OR max_sequence <> route_count;
```

预期返回空结果。

## 7. 验证上海方向、到站和调度

检查同一上海线路 ID 的两个方向是否独立保存：

```sql
SELECT
    shanghai_line_id,
    COUNT(*) AS direction_count,
    GROUP_CONCAT(direction ORDER BY direction) AS directions
FROM `lines`
WHERE shanghai_line_id IS NOT NULL
GROUP BY shanghai_line_id
HAVING direction_count = 2
ORDER BY shanghai_line_id;
```

样例中同时返回两个方向的线路应显示 `directions = '0,1'`。

检查本次上海运行的到站快照数量：

```sql
SELECT
    ir.id AS run_id,
    ir.status,
    ir.received_count,
    ir.skipped_count,
    COUNT(ai.id) AS arrival_count
FROM `ingestion_runs` AS ir
LEFT JOIN `arrival_infos` AS ai ON ai.ingestion_run_id = ir.id
WHERE ir.source = 'shanghai'
  AND ir.task_type = 'nearby_import'
GROUP BY ir.id, ir.status, ir.received_count, ir.skipped_count
ORDER BY ir.id DESC;
```

最新成功或部分成功运行预期：`received_count = 50`、`arrival_count = 42`，并且
`skipped_count >= 1`。失败运行的 `arrival_count` 应为 0。

检查是否违反同批次快照唯一性：

```sql
SELECT ingestion_run_id, line_id, stop_id, COUNT(*) AS duplicate_count
FROM `arrival_infos`
GROUP BY ingestion_run_id, line_id, stop_id
HAVING duplicate_count > 1;
```

预期返回空结果。

检查调度父子记录：

```sql
SELECT
    ir.id AS run_id,
    COUNT(DISTINCT ds.id) AS schedule_count,
    COUNT(dc.id) AS car_count
FROM `ingestion_runs` AS ir
LEFT JOIN `dispatch_schedules` AS ds ON ds.ingestion_run_id = ir.id
LEFT JOIN `dispatch_cars` AS dc ON dc.schedule_id = ds.id
WHERE ir.source = 'shanghai'
  AND ir.status IN ('success', 'partial')
GROUP BY ir.id
ORDER BY ir.id DESC
LIMIT 1;
```

预期：`schedule_count = 37`、`car_count = 95`。

检查孤立调度车辆：

```sql
SELECT dc.id
FROM `dispatch_cars` AS dc
LEFT JOIN `dispatch_schedules` AS ds ON ds.id = dc.schedule_id
WHERE ds.id IS NULL;
```

预期返回空结果。

## 8. 验证重复导入幂等性

先记录数量：

```sql
SELECT
    (SELECT COUNT(*) FROM `ingestion_runs`) AS runs_before,
    (SELECT COUNT(*) FROM `arrival_infos`) AS arrivals_before,
    (SELECT COUNT(*) FROM `dispatch_schedules`) AS schedules_before,
    (SELECT COUNT(*) FROM `dispatch_cars`) AS cars_before;
```

再次执行完全相同的命令：

```bash
python -m app.commands.import_samples \
  ../bus_stop_by_name.json \
  ../bus_line_raw_gaode.json \
  ../raw_result.json
```

然后再次查询：

```sql
SELECT
    (SELECT COUNT(*) FROM `ingestion_runs`) AS runs_after,
    (SELECT COUNT(*) FROM `arrival_infos`) AS arrivals_after,
    (SELECT COUNT(*) FROM `dispatch_schedules`) AS schedules_after,
```

预期所有 `after` 均与对应的 `before` 相同。命令会输出原来的三个运行 ID。

## 9. 验证异常回滚和 failed 记录

在 `backend` 目录执行以下命令。它只在内存中修改 JSON，把第二站改成重复的站序 1，
不会修改样例文件：

```bash
python - <<'PY'
import json
from pathlib import Path

from app.db.session import SessionFactory
from app.services.ingestion import import_amap_lines

payload = json.loads(Path('../bus_line_raw_gaode.json').read_text(encoding='utf-8'))
payload['buslines'][0]['busstops'][1]['sequence'] = '1'

with SessionFactory() as session:
    try:
        import_amap_lines(session, payload, request_key='stage5-invalid-route-test')
    except Exception as exc:
        print(type(exc).__name__, exc)
PY
```

预期终端包含：

```text
AmapParseError ...站序...
```

检查运行记录：

```sql
SELECT id, source, task_type, request_key, status, error_message
FROM `ingestion_runs`
WHERE request_key = 'stage5-invalid-route-test'
ORDER BY id DESC
LIMIT 1;
```

预期 `status = 'failed'`，错误摘要包含站序问题。由于解析在写入线路业务数据前完成，本次失败
不会改变 `lines`、`stops` 或 `line_routes`。

## 11. 验收结论

同时满足以下条件即可认为阶段 5 通过：

1. 三个样例可由一条命令导入；
2. 两个高德线路方向均有连续的 29 条站序；
3. 最新上海运行产生 42 条到站快照、37 条调度快照和 95 条调度车辆明细；
4. 缺失 `sai` 的记录没有生成空到站快照；
5. 重复执行相同命令不增加运行、快照和调度数量；
6. 非法站序使业务事务回滚，同时保留 `failed` 运行记录；
7. 不存在重复到站快照、重复站序或孤立调度车辆。
