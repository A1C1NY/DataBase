# 阶段 3：首次 Alembic 迁移执行指南

本文档从当前项目状态出发，完成以下目标：

1. 使用同步 Engine 执行 Alembic 在线迁移；
2. 从 `Settings` 读取数据库 URL；
3. 加载全部 ORM metadata；
4. 在空数据库上生成包含 10 张业务表的首次迁移；
5. 完成 `upgrade -> downgrade -> upgrade` 验证。

本文档只使用 Shell、MySQL 客户端和 Alembic，不使用临时 Python 脚本。

## 1. 当前状态与错误原因

当前 `alembic/env.py` 已经完成阶段 3 的三个环境要求：

- `engine_from_config()` 创建同步 Engine；
- `get_settings().database_url` 提供数据库 URL；
- `import app.models` 和 `Base.metadata` 加载全部模型。

此前的 `1045 Access denied` 是数据库 URL 写反造成的。错误配置实际被解析为：

```text
用户名：transit_system_migration_test
数据库：transit_system
```

正确 URL 格式是：

```text
mysql+pymysql://用户名:密码@主机:端口/数据库名?charset=utf8mb4
```

本次应使用：

```text
mysql+pymysql://transit_app:实际密码@127.0.0.1:3306/transit_system_migration_test?charset=utf8mb4
```

注意：`sudo` 只用于进入 MySQL 管理终端，不要执行 `sudo alembic`。

## 2. 进入项目并启用虚拟环境

前置条件：当前用户能够读取 `.database` 虚拟环境。

```bash
cd ~/桌面/design/DataBase/backend
source ../.database/bin/activate
unset PYTHONPATH
pwd
alembic --version
```

预期工作目录：

```text
/home/alcony/桌面/design/DataBase/backend
```

`alembic --version` 必须正常输出版本号。失败时停止，不要继续。

## 3. 创建空迁移测试数据库并授权

前置条件：当前 Linux 用户具有 `sudo mysql` 权限，MySQL 服务已经启动。

```bash
sudo mysql
```

进入 `mysql>` 后依次执行：

```sql
CREATE DATABASE IF NOT EXISTS transit_system_migration_test
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_0900_ai_ci;

GRANT SELECT, INSERT, UPDATE, DELETE,
      CREATE, ALTER, INDEX, DROP, REFERENCES
ON transit_system_migration_test.*
TO 'transit_app'@'%';

FLUSH PRIVILEGES;

SHOW GRANTS FOR 'transit_app'@'%';

SELECT COUNT(*) AS existing_tables
FROM information_schema.tables
WHERE table_schema = 'transit_system_migration_test';
```

继续执行的必要条件：

```text
existing_tables = 0
```

如果结果不是 `0`，不要生成迁移，也不要删除现有表。改用一个全新的数据库名，并同步替换本文后续命令中的数据库名。

退出 MySQL：

```sql
EXIT;
```

## 4. 修正 `.env` 数据库 URL

前置条件：知道 `transit_app` 的实际密码。

打开 `backend/.env`，只修正 `DATABASE_URL`：

```env
DATABASE_URL=mysql+pymysql://transit_app:实际密码@127.0.0.1:3306/transit_system_migration_test?charset=utf8mb4
```

不要把 `transit_system_migration_test` 放在 `://` 后面；该位置是用户名。

如果密码包含 `@`、`:`、`/`、`#` 或 `%`，必须先进行 URL 编码，否则连接串会被错误解析。

## 5. 使用 MySQL 客户端验证账户和空库

前置条件：第 3 节授权成功，第 4 节使用的用户名和密码正确。

```bash
mysql -h 127.0.0.1 -P 3306 -u transit_app -p transit_system_migration_test
```

输入 `transit_app` 的密码。进入 `mysql>` 后执行：

```sql
SELECT CURRENT_USER(), DATABASE();

SELECT COUNT(*) AS existing_tables
FROM information_schema.tables
WHERE table_schema = DATABASE();
```

预期：

```text
CURRENT_USER() = transit_app@%
DATABASE() = transit_system_migration_test
existing_tables = 0
```

任何一项不符合都应停止。确认后退出：

```sql
EXIT;
```

## 6. 确认迁移目录没有旧 revision

前置条件：尚未执行新的 `revision --autogenerate`。

```bash
find alembic/versions -maxdepth 1 -type f -name '*.py' -print
```

首次迁移前预期没有输出。

如果发现之前错误生成的 revision，不要继续生成第二个 revision。先将旧文件移到备份目录：

```bash
mkdir -p ../alembic_revision_backup
mv alembic/versions/*.py ../alembic_revision_backup/
```

再次确认：

```bash
find alembic/versions -maxdepth 1 -type f -name '*.py' -print
```

必须没有输出。

## 7. 生成首次迁移

生成前必须同时满足：

- 当前目录是 `backend`；
- 虚拟环境已启用；
- `.env` 指向 `transit_system_migration_test`；
- 应用账户能够连接该数据库；
- 测试数据库中没有任何表；
- `alembic/versions` 中没有旧 revision。

执行：

```bash
alembic revision --autogenerate -m "create initial tables"
```

正常输出应包含多条：

```text
Detected added table ...
Detected added index ...
Generating ... done
```

检查迁移文件：

```bash
find alembic/versions -maxdepth 1 -type f -name '*.py' -print
rg -n 'op\.create_table|op\.drop_table' alembic/versions
```

必要条件：

- `upgrade()` 中有 10 个 `op.create_table(...)`；
- `downgrade()` 中有 10 个 `op.drop_table(...)`。

统计命令：

```bash
rg -c 'op\.create_table' alembic/versions/*.py
rg -c 'op\.drop_table' alembic/versions/*.py
```

两个结果都必须为 `10`。否则停止，不要执行 `upgrade head`。

## 8. 人工检查迁移文件

打开新生成的 `alembic/versions/*.py`，逐项确认：

- 10 张业务表全部存在；
- 主键使用 `BIGINT UNSIGNED`；
- 时间戳使用 `DATETIME(3)`；
- `updated_at` 包含 `ON UPDATE CURRENT_TIMESTAMP(3)`；
- 表使用 `InnoDB`、`utf8mb4` 和 `utf8mb4_0900_ai_ci`；
- 外键删除规则与构建指南一致；
- 唯一约束没有被生成成普通索引；
- `line_routes (line_id, stop_id)` 是普通索引，不是唯一索引；
- `idx_arrival_stop_time` 为 `(stop_id, collected_at DESC)`；
- `downgrade()` 按外键依赖的逆序删除表。

阶段 2 的结构契约测试可用于再次检查 ORM：

```bash
pytest -q tests/integration/test_database_contracts.py
```

该测试通过只说明 ORM 符合指南；仍须阅读实际生成的迁移文件。

## 9. 第一次升级

前置条件：第 7、8 节全部通过。

```bash
alembic upgrade head
alembic current
```

然后连接测试数据库：

```bash
mysql -h 127.0.0.1 -P 3306 -u transit_app -p transit_system_migration_test
```

执行：

```sql
SHOW TABLES;

SELECT COUNT(*) AS business_tables
FROM information_schema.tables
WHERE table_schema = DATABASE()
  AND table_type = 'BASE TABLE'
  AND table_name <> 'alembic_version';

SELECT version_num FROM alembic_version;
```

必要结果：

```text
business_tables = 10
```

`alembic_version.version_num` 应等于迁移文件中的 revision ID。

检查特殊降序索引：

```sql
SHOW INDEX FROM arrival_infos
WHERE Key_name = 'idx_arrival_stop_time';
```

`collected_at` 行的 `Collation` 必须为 `D`。

退出：

```sql
EXIT;
```

## 10. 降级到 base

前置条件：第一次升级成功，且当前连接的确是迁移测试数据库。

```bash
alembic downgrade base
alembic current
```

连接数据库：

```bash
mysql -h 127.0.0.1 -P 3306 -u transit_app -p transit_system_migration_test
```

执行：

```sql
SELECT COUNT(*) AS business_tables
FROM information_schema.tables
WHERE table_schema = DATABASE()
  AND table_type = 'BASE TABLE'
  AND table_name <> 'alembic_version';

SELECT * FROM alembic_version;
```

必要结果：

```text
business_tables = 0
```

`alembic_version` 表可能保留，但其中不应有 revision 记录。

退出：

```sql
EXIT;
```

## 11. 再次升级

前置条件：第 10 节确认业务表数量为 `0`。

```bash
alembic upgrade head
alembic current
```

再次连接数据库并检查：

```bash
mysql -h 127.0.0.1 -P 3306 -u transit_app -p transit_system_migration_test
```

```sql
SELECT COUNT(*) AS business_tables
FROM information_schema.tables
WHERE table_schema = DATABASE()
  AND table_type = 'BASE TABLE'
  AND table_name <> 'alembic_version';

SELECT version_num FROM alembic_version;

EXIT;
```

最终必要结果：

```text
business_tables = 10
```

至此才满足阶段 3 的完成标准：空数据库可以升级，随后能够降级并再次升级。

## 12. 原 `transit_system` 数据库如何处理

完成上述验证前，不要对原 `transit_system` 执行 `upgrade head`，因为它已经存在 10 张业务表。

首次迁移验证完成后，如果确认原数据库与迁移结果完全一致，可以再评估：

```bash
alembic stamp head
```

`stamp` 会修改目标数据库的 Alembic 版本记录。执行前必须把 `.env` 切回原数据库并再次确认结构，因此不属于本次空库迁移验证流程，不应提前执行。
